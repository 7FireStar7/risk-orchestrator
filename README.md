# Risk Orchestrator

MVP-оркестратор параллельных процессов оценки рисков. Решение кейса заочного этапа турнира, команда «Фанаты ТОП-ИТ».

## Проблема

Процессы оценки рисков (кредитный, рыночный, ликвидность и др.) пересекаются:
- по времени (ручной запуск против регламентного);
- по источникам данных (одни и те же источники, в том числе за одну дату);
- при одновременном запуске N пользователями одного процесса за разные даты или разных процессов за одну дату.

Результат: конфликты, взаимные блокировки, ошибки выполнения и искажение данных.

## Решение

Оркестратор управляет запусками так, чтобы пересечения были невозможны:

1. **Ресурсная модель.** Каждый запуск занимает набор ресурсов: `proc:{процесс}:{дата}` и `src:{источник}:{дата}` для каждого источника процесса.
2. **Всё или ничего.** Запуск стартует, только когда свободны все его ресурсы. Если занят хотя бы один, запуск ждёт в очереди, и пользователь видит причину.
3. **Защита на уровне БД.** `PRIMARY KEY` на ресурсе в таблице `run_locks` физически не даёт двум запускам занять один ресурс. Решения диспетчера сериализуются через `pg_advisory_xact_lock`.
4. **Нет взаимных блокировок.** Ресурсы берутся атомарно все сразу, поэтому циклическое ожидание невозможно.
5. **Приоритеты и aging.** Регламентный запуск приоритетнее ручного, ручной со временем получает повышение. Ресурсы запусков, стоящих выше в очереди, резервируются, чтобы избежать голодания.
6. **Дедупликация.** Повторный запуск того же процесса за ту же дату отклоняется (HTTP 409).
7. **Восстановление.** После перезапуска сервиса зависшие запуски помечаются FAILED, блокировки снимаются.

## Правила конфликтов

| Ситуация | Результат |
|---|---|
| Один процесс, одна дата | Запрещено параллельно (дубликат) |
| Разные процессы, общий источник, одна дата | Последовательно, второй ждёт |
| Один процесс, разные даты | Параллельно, если не пересекаются ресурсы |
| Регламентный против ручного | Регламентный первым, ручной ждёт с причиной |

## Стек

Python, FastAPI, PostgreSQL (psycopg), React (Vite).

## Структура

```
backend/     FastAPI, оркестратор, схема БД
frontend/    React-интерфейс (Vite)
simulator/   симулятор нагрузки и результаты прогона (simulator/out)
docs/        аналитика и системные требования
```

## Запуск

Нужны Python 3.12+, Node.js 18+ и PostgreSQL. Создайте пустую базу `risk_orchestrator`.

Терминал 1, бэкенд:
```
copy .env.example .env      # впишите пароль в DATABASE_URL
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r backend\requirements.txt
cd backend
python -m uvicorn main:app --reload
```

Терминал 2, интерфейс:
```
cd frontend
npm install
npm run dev
```

Интерфейс: http://localhost:5173, Swagger: http://127.0.0.1:8000/docs.
В интерфейсе кнопка «Демо-сценарий» запускает серию процессов с конфликтами и дубликатом.

## Симулятор

Один сценарий (36 заявок: 6 регламентных, 30 ручных от 8 пользователей) прогоняется тремя способами.
Значение `--scale` должно совпадать с `TIME_SCALE` в `.env`.
```
python simulator\simulate.py --scale 1
```
Результаты (`execution_log.csv`, `events.csv`, `report.md`) сохраняются в `simulator/out/`.

| Показатель | Без координации | Наивные блокировки | Оркестратор |
|---|---|---|---|
| Конфликты по ресурсам | 132 | не измерялись | **0** |
| Зависшие запуски (взаимные блокировки) | не применимо | 24 из 36 | **0** |
| Пик параллельных запусков | 23 | не применимо | 5 |

Короткая длительность без координации мнимая: при 132 конфликтах данные искажены.

## Ограничения MVP

- Воркеры реализованы потоками и имитируют работу через `sleep`. В продакшене их выносят в отдельный сервис (Celery, Airflow, Temporal), модель блокировок остаётся прежней.
- Выполняющийся запуск не вытесняется приоритетным.
- Отмена выполняющегося запуска сразу снимает блокировки; для реального расчёта отмена должна быть кооперативной.
- В интерфейсе нет редактора расписания регламента и справочников процессов и источников.
- Результаты получены на одном сценарии (`seed=42`).
