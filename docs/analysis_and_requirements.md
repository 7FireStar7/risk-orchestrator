# 1. Постановка и исходные данные

Система оценки рисков запускает бизнес-процессы по регламенту и вручную. Процессы пересекаются по времени и по источникам данных, из-за чего возникают конфликты, взаимные блокировки и искажение данных.

Для анализа построена синтетическая модель компании:

- **6 процессов:** кредитный, рыночный, ликвидность, операционный, контрагентский риск, стресс-тестирование;
- **5 источников данных:** Core Banking, рыночные котировки, главная книга, реестр контрагентов, лимиты;
- **16 связей «процесс → источник»** (матрица зависимостей, показана на вкладке «Журнал и матрица» интерфейса);
- **сценарий нагрузки:** 36 заявок на запуск (6 регламентных и 30 ручных от 8 пользователей) за 3 расчётные даты, фиксированный `seed=42`.

Один и тот же сценарий прогнан тремя способами:

| Вариант | Что это |
|--|----------|
| **A** | Без координации: каждая заявка стартует сразу |
| **B** | Наивные блокировки: ресурсы берутся по одному, в произвольном порядке |
| **C** | Разработанный оркестратор |

Все варианты работали на одной шкале времени (`scale=1`). Исходные данные: `simulator/out/execution_log.csv`, `events.csv`, `report.md`.

# 2. Узкие места процесса

| № | Узкое место | Как проявляется | Доказательство из симуляции |
|--|--------|------------|----------------|
| 1 | Пересечение запусков по времени и ресурсам | Запуски с общими источниками выполняются одновременно и портят друг другу данные | Вариант A: **132** пары запусков с общим ресурсом и пересекающимся временем, пик **23** параллельных запуска |
| 2 | Общие источники данных | Несколько процессов читают один источник за одну дату | `limits` и `market_feed` используются 4 процессами из 6. Из 31 ожидания у оркестратора: `limits` 9, `gl_ledger` 8, `core_banking` 6, `market_feed` 5, `cpty_registry` 3 |
| 3 | Дублирующие запуски | Один процесс за одну дату запускают повторно (двойное нажатие, два пользователя) | **18 из 36** заявок (50%) повторяли уже выполняющийся или ожидающий запуск |
| 4 | Взаимные блокировки | Запуски берут общие ресурсы по одному и в разном порядке, затем ждут друг друга | Вариант B: **24 из 36** запусков зависли по таймауту, завершились только 12 |
| 5 | Эффект «обоза»: короткие процессы ждут за длинными | Долгий процесс с несколькими источниками блокирует остальных | Операционный риск (один источник, 7.1 с работы) ждал **84.5 с**, то есть в 12 раз дольше своей работы. Стресс-тестирование держит 4 источника из 5 в среднем 33 с |
| 6 | Ресурсы удерживаются весь запуск целиком | Источник занят, пока идёт весь расчёт, хотя читается, скорее всего, в начале | Суммарное ожидание **519 с** против **331 с** суммарного счёта. Пик параллелизма всего 5 при 18 принятых запусках |
| 7 | Нет приоритетов и видимости очереди | Срочное ждёт наравне с ручным, пользователь не знает причины ожидания | Ручные запуски ждали в среднем 32.9 с, регламентные 20.8 с (разница в 1.6 раза). Без оркестратора причины ожидания не фиксируются вообще |
| 8 | Сбой оставляет блокировки | Упавший запуск не освобождает ресурсы | 3 из 18 запусков завершились имитированным сбоем (10%). Без обработки сбоев их ресурсы остались бы занятыми |

# 3. ИИ-анализ процесса

## 3.1 Как проводился анализ

Анализ выполнил ИИ-ассистент Claude (Anthropic) по данным симуляции. Числа в выводах пересчитаны скриптом по исходным CSV, а не взяты «на глаз».

**Вход:** описание кейса, матрица зависимостей (16 связей), `execution_log.csv` (18 запусков), `events.csv` (журнал событий), сводка прогона A/B/C.

**Промпт:**

> Ты аналитик бизнес-процессов и инженер по надёжности распределённых систем. Контекст: в компании система оценки рисков запускает процессы вручную и по регламенту; процессы пересекаются по времени и по источникам данных, возникают конфликты и взаимные блокировки. Дано: (1) матрица «процесс × источник данных»; (2) execution_log.csv: процесс, дата, тип запуска, пользователь, ожидание, выполнение, статус; (3) events.csv: журнал событий оркестратора с причинами ожидания; (4) сводка прогона трёх вариантов: без координации, наивные блокировки, оркестратор. Задачи: (а) найди узкие места процесса и ранжируй по влиянию; (б) для каждого приведи числовое доказательство из данных; (в) предложи системные требования к модулю-оркестратору; (г) предложи улучшения и оцени риски. Не придумывай числа: используй только данные, допущения помечай явно.

## 3.2 Что выявил анализ

1. **Главный источник потерь** это конфликты по общим источникам (132 конфликтные пары в варианте A). Конфликт определяется парой «источник + дата», а не процессом целиком.
2. **Самые «горячие» источники:** `limits` (9 ожиданий) и `gl_ledger` (8). `gl_ledger` читают лишь три процесса, но среди них самый короткий процесс (операционный риск), у которого отношение ожидания к счёту максимально.
3. **Простои несимметричны.** Длинные процессы (стресс-тестирование) занимают много источников и задерживают короткие. Для коротких запусков отношение «ожидание / счёт» достигает 12.
4. **Приоритет работает, но не устраняет ожидание.** Регламентные ждут в 1.6 раза меньше, чем ручные, но 20.8 с в среднем всё равно заметно.
5. **Защита от голодания срабатывает редко** (2 из 31 ожидания), основная причина ожидания это просто занятый ресурс (29 из 31).

## 3.3 Предложения ИИ по улучшению

| Предложение | Ожидаемый эффект | Риск |
|---|---|---|
| Разделяемые (читающие) блокировки для источников, которые процессы только читают | Одновременная работа процессов с общим источником без конфликта | Нужна гарантия неизменности источника на время расчёта |
| Поэтапное освобождение источников: снять блокировку источника после стадии загрузки | Меньше простоя, выше параллелизм (сейчас ожидание в 1.6 раза больше счёта) | Усложнение модели процесса: нужны стадии |
| Оценка времени старта (ETA) в интерфейсе на основе средней длительности процессов | Пользователь планирует работу, меньше повторных заявок | Оценка приблизительна |
| Политика «короткие вперёд» или лимит ожидания ручного запуска | Снижает эффект «обоза» | Нужно сохранить приоритет регламента |
| Безопасное вытеснение ручного запуска регламентным в контрольных точках | Регламентный не ждёт ручной | Требует контрольных точек в расчёте |

# 4. Системные требования к модулю-оркестратору

## 4.1 Функциональные

| ID | Требование | Реализация в MVP |
|--|-------------|--------|
| FR-1 | Каталог процессов, источников данных и матрица зависимостей | Таблицы `processes`, `data_sources`, `process_sources` |
| FR-2 | Ресурсная модель: ресурс запуска это `proc:{процесс}:{дата}` и `src:{источник}:{дата}` для каждого источника процесса | `orchestrator.res_keys` |
| FR-3 | Атомарный захват: запуск стартует только при свободных всех ресурсах, иначе ждёт целиком | `orchestrator.dispatch` |
| FR-4 | Очередь с приоритетами: регламентный (100) выше ручного (50); старение: +1 к приоритету за каждые `AGING_SEC` ожидания | `dispatch`, параметр `AGING_SEC` |
| FR-5 | Резервирование ресурсов запусков, стоящих выше в очереди (защита от голодания) | словарь `reserved` в `dispatch` |
| FR-6 | Дедупликация: повтор «процесс + дата» в статусах QUEUED и RUNNING отклоняется (HTTP 409) | `orchestrator.submit` |
| FR-7 | Отмена запуска в очереди и выполняющегося с освобождением ресурсов | `orchestrator.cancel` |
| FR-8 | Обработка сбоев: освобождение ресурсов при FAILED; восстановление после перезапуска сервиса | `finish`, `recover` |
| FR-9 | Журнал событий (SUBMITTED, WAITING, STARTED, DONE, FAILED, CANCELLED) с причиной ожидания | таблица `event_log` |
| FR-10 | Предпроверка конфликтов до запуска: какие ресурсы заняты и кем | `POST /api/runs/preview` |
| FR-11 | Интерфейс: дашборд, очередь с причинами, таймлайн, матрица, журнал, форма запуска | React-приложение `frontend/` |
| FR-12 | REST API для интерфейса и внешних планировщиков | FastAPI, документация `/docs` |

## 4.2 Нефункциональные

| ID | Требование | Как обеспечивается и проверяется |
|--|-------------|-----------|
| NFR-1 | **Корректность:** два запуска с общим ресурсом никогда не выполняются одновременно | `PRIMARY KEY` на ресурсе в `run_locks`; симулятор проверяет отсутствие пересечений, результат 0 |
| NFR-2 | **Отсутствие взаимных блокировок** | «Всё или ничего» плюс сериализация решений диспетчера через `pg_advisory_xact_lock`; в варианте B зависло 24 запуска, в C 0 |
| NFR-3 | **Ограниченное ожидание** (нет голодания) | Старение приоритета и резервирование ресурсов |
| NFR-4 | **Наблюдаемость:** причина каждого ожидания видна пользователю | Поле `wait_reason`, журнал событий, интерфейс |
| NFR-5 | **Воспроизводимость испытаний** | Симулятор с фиксированным `seed`, CSV-логи в `simulator/out/` |
| NFR-6 | **Устойчивость к перезапуску** | Состояние хранится в PostgreSQL, `recover()` при старте |
| NFR-7 | **Масштабируемость** | API без состояния, воркеры выносимы в отдельный сервис (Celery, Airflow, Temporal) без изменения модели блокировок |

# 5. Варианты решения

| Подход | Плюсы | Минусы | Вывод |
|---|---|---|---|
| Блокировки в памяти приложения (мьютексы) | Просто реализовать | Не работают при нескольких экземплярах сервиса, теряются при перезапуске, нет аудита | Не подходит |
| Готовый оркестратор (Airflow, Temporal и аналоги) | Зрелые инструменты, расписания, повторы | Тяжёлая инфраструктура; атомарный захват нескольких ресурсов «источник + дата», как правило, приходится реализовывать самим | Избыточен для MVP, разумен для продакшена |
| **Блокировки на уровне БД (выбрано)** | Гарантия на уровне хранилища, переживает перезапуск, видна в таблицах, легко аудируется | БД становится точкой координации; при очень высокой нагрузке нужно масштабирование | **Выбрано для MVP** |

**Рекомендация для продакшена:** сохранить ресурсную модель и таблицу блокировок, а выполнение расчётов передать внешнему оркестратору или очереди задач.

# 6. Результаты проверки

| Показатель | A. Без координации | B. Наивные блокировки | C. Оркестратор |
|--------|----|----|----|
| Конфликты (пересечение ресурсов во времени) | 132 | не измерялись | **0** |
| Зависшие по таймауту (взаимные блокировки) | не применимо | 24 из 36 | **0** |
| Пик параллельных запусков | 23 | не применимо | 5 |
| Отклонено как дубликаты | 0 | 0 | 18 |
| Завершено успешно / с ошибкой | не применимо | 12 / 24 | 15 / 3 |
| Среднее ожидание, регламентные, с | 0 | не применимо | 20.8 |
| Среднее ожидание, ручные, с | 0 | не применимо | 32.9 |
| Длительность сценария, с | 50 | не применимо | 110 |

**Как читать таблицу.** Короткая длительность варианта A мнимая: при 132 конфликтах данные искажены, а результаты ненадёжны. Оркестратор тратит больше времени (110 с против 50 с), но за счёт этого все 18 принятых запусков выполнены без пересечений. Ошибки в варианте C (3 из 18) это имитация сбоев расчёта (вероятность 10%), а не конфликты. Дубликаты (18) отклонены сознательно: это защита от повторных заявок на уже идущий расчёт.

# 7. Ограничения MVP и развитие

- Воркеры реализованы потоками и имитируют расчёт через `sleep`. Настоящей риск-математики в MVP нет.
- Выполняющийся запуск не вытесняется другим, даже более приоритетным: регламентный запуск может ждать ручной.
- Отмена выполняющегося запуска сразу снимает блокировки. Для реального расчёта отмена должна быть кооперативной: ресурсы освобождаются после фактической остановки воркера.
- Результаты получены на одном сценарии (`seed=42`, 36 заявок). Для статистической оценки нужны серии прогонов с разными `seed`.
- Направления развития: разделяемые блокировки для источников только на чтение, поэтапное освобождение ресурсов, оценка времени старта (ETA), безопасное вытеснение ручных запусков, вынос воркеров во внешний оркестратор.
